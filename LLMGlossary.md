  <h1>OpenAI Playground / Anthropic Console glossary</h1>

  <p>
    Use this vocabulary to discuss both tools fluently. The products overlap—a
    browser interface for testing models and prompts—but their APIs and
    terminology differ.
  </p>

  <h2>Core concepts</h2>

  <table>
    <thead>
      <tr>
        <th scope="col">Term</th>
        <th scope="col">Meaning</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><strong>Model</strong></td>
        <td>
          The underlying AI system that generates a response. Models differ in
          capability, speed, context size, modalities, and price.
        </td>
      </tr>
      <tr>
        <td><strong>Prompt</strong></td>
        <td>
          The complete input sent to the model: instructions, conversation
          history, examples, data, and sometimes tool definitions.
        </td>
      </tr>
      <tr>
        <td><strong>System instructions</strong></td>
        <td>
          High-level behavioral guidance supplied by the developer, such as
          role, goals, constraints, tone, or output rules. OpenAI may call these
          “instructions”; Anthropic commonly calls them a “system prompt.”
        </td>
      </tr>
      <tr>
        <td><strong>User message</strong></td>
        <td>The task or content supplied by the end user.</td>
      </tr>
      <tr>
        <td><strong>Assistant response</strong></td>
        <td>
          The model-generated output. In API results, it may contain text, tool
          calls, reasoning-related metadata, or other content blocks.
        </td>
      </tr>
      <tr>
        <td><strong>Conversation / message history</strong></td>
        <td>
          The sequence of prior user and assistant turns included in the
          request. The model has no automatic access to earlier turns unless
          they are preserved and sent again, or managed by a stateful product.
        </td>
      </tr>
      <tr>
        <td><strong>Context window</strong></td>
        <td>
          The maximum amount of input and output the model can handle in one
          request. It is the model’s temporary working memory, not its training
          data.
        </td>
      </tr>
      <tr>
        <td><strong>Token</strong></td>
        <td>
          A small unit of text processed by the model. Words, parts of words,
          punctuation, and spaces may each consume tokens.
        </td>
      </tr>
      <tr>
        <td><strong>Input tokens</strong></td>
        <td>Tokens in the prompt and other request data.</td>
      </tr>
      <tr>
        <td><strong>Output tokens</strong></td>
        <td>Tokens generated by the model.</td>
      </tr>
      <tr>
        <td><strong>Token usage</strong></td>
        <td>
          The input and output token counts associated with a request; it is
          used for billing, capacity planning, and debugging.
        </td>
      </tr>
      <tr>
        <td><strong>Latency</strong></td>
        <td>
          The time between sending a request and receiving the response.
        </td>
      </tr>
      <tr>
        <td><strong>Temperature</strong></td>
        <td>
          A sampling control that generally affects variation. Lower values tend
          to produce more consistent outputs; higher values tend to produce
          more diverse outputs.
        </td>
      </tr>
      <tr>
        <td><strong>Maximum output tokens</strong></td>
        <td>
          A ceiling on how long the generated response may be. It limits
          length, not necessarily quality.
        </td>
      </tr>
      <tr>
        <td><strong>Stop reason</strong></td>
        <td>
          The API’s explanation for why generation ended—for example, natural
          completion, reaching the output limit, or producing a tool call.
        </td>
      </tr>
    </tbody>
  </table>

  <h2>OpenAI terms</h2>

  <p>
    OpenAI’s current API direction centers on the
    <strong>Responses API</strong>, which supports direct model requests for
    text, images, structured output, and tool-based workflows.
  </p>

  <table>
    <thead>
      <tr>
        <th scope="col">Term</th>
        <th scope="col">Meaning</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><strong>OpenAI Playground</strong></td>
        <td>
          A browser-based environment for trying OpenAI models, prompts,
          parameters, tools, and output formats before writing application
          code.
        </td>
      </tr>
      <tr>
        <td><strong>Responses API</strong></td>
        <td>
          OpenAI’s general-purpose interface for model responses, including
          text, images, structured outputs, and tool-based workflows.
        </td>
      </tr>
      <tr>
        <td><strong>Chat Completions API</strong></td>
        <td>
          An older, still-recognized interface organized around a list of chat
          messages. It is often encountered in existing code and tutorials.
        </td>
      </tr>
      <tr>
        <td><strong>Input</strong></td>
        <td>
          The content provided to the Responses API. It can be a simple string
          or a richer sequence of messages and content parts.
        </td>
      </tr>
      <tr>
        <td><strong>Instructions</strong></td>
        <td>
          OpenAI’s field or concept for high-level guidance to the model,
          broadly analogous to a system prompt.
        </td>
      </tr>
      <tr>
        <td><strong>Response object</strong></td>
        <td>
          The structured API result returned by the Responses API. It can
          include output items, tool calls, status information, and usage.
        </td>
      </tr>
      <tr>
        <td><strong>Output item</strong></td>
        <td>
          One unit inside a response, such as generated text, a function call,
          a web-search result, or another response component.
        </td>
      </tr>
      <tr>
        <td><strong>Function calling</strong></td>
        <td>
          A mechanism in which the model emits a structured request for your
          application to call a function. Your code executes the function and
          sends the result back.
        </td>
      </tr>
      <tr>
        <td><strong>Tool</strong></td>
        <td>
          A capability the model can invoke, such as web search, file search,
          code execution, or a developer-defined function.
        </td>
      </tr>
      <tr>
        <td><strong>Structured Outputs</strong></td>
        <td>
          A feature that constrains the model’s response to conform to a
          supplied JSON Schema, useful when software must reliably parse the
          result.
        </td>
      </tr>
      <tr>
        <td><strong>JSON mode</strong></td>
        <td>
          A looser request for JSON-formatted output. JSON mode does not
          necessarily guarantee that the result matches a particular schema.
        </td>
      </tr>
      <tr>
        <td><strong>Vision</strong></td>
        <td>
          The ability to analyze image content supplied to the model.
        </td>
      </tr>
      <tr>
        <td><strong>Multimodal</strong></td>
        <td>
          A request or response involving multiple modalities, such as text and
          images, or text and audio.
        </td>
      </tr>
      <tr>
        <td><strong>File search</strong></td>
        <td>
          A retrieval tool that lets a model search uploaded or connected files
          for relevant information.
        </td>
      </tr>
      <tr>
        <td><strong>Web search</strong></td>
        <td>
          A tool that allows the model or agent workflow to retrieve current
          information from the web.
        </td>
      </tr>
      <tr>
        <td><strong>Agents SDK</strong></td>
        <td>
          A code-first framework for building agents that coordinate tools,
          handoffs, approvals, tracing, and execution environments.
        </td>
      </tr>
      <tr>
        <td><strong>Handoff</strong></td>
        <td>
          The transfer of responsibility from one agent or workflow component
          to another specialized agent.
        </td>
      </tr>
      <tr>
        <td><strong>Trace / tracing</strong></td>
        <td>
          A record of an agent’s steps, tool calls, decisions, and outputs used
          for debugging and evaluation.
        </td>
      </tr>
      <tr>
        <td><strong>Evals</strong></td>
        <td>
          Repeatable tests used to measure whether a prompt, model, or
          application performs acceptably on representative tasks.
        </td>
      </tr>
      <tr>
        <td><strong>Fine-tuning</strong></td>
        <td>
          Additional training of a model on task-specific examples so it
          behaves differently for a particular use case.
        </td>
      </tr>
      <tr>
        <td><strong>Distillation</strong></td>
        <td>
          Transferring useful behavior from a larger or more capable model into
          a smaller, cheaper, or faster model.
        </td>
      </tr>
      <tr>
        <td><strong>Prompt caching</strong></td>
        <td>
          Reusing a stable prefix of repeated requests to reduce processing cost
          and latency.
        </td>
      </tr>
    </tbody>
  </table>

  <h2>Anthropic terms</h2>

  <p>
    Anthropic’s current platform distinguishes direct model access through the
    <strong>Messages API</strong> from managed agent infrastructure.
  </p>

  <table>
    <thead>
      <tr>
        <th scope="col">Term</th>
        <th scope="col">Meaning</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><strong>Claude Console</strong></td>
        <td>
          Anthropic’s developer portal for API keys, workspaces, usage, models,
          documentation, and experimentation.
        </td>
      </tr>
      <tr>
        <td><strong>Claude Playground</strong></td>
        <td>
          The current browser interface for trying Claude models and API
          features inside the Console. It replaced the legacy Workbench.
        </td>
      </tr>
      <tr>
        <td><strong>Workbench</strong></td>
        <td>
          Anthropic’s former experimentation environment. The legacy version
          supported saved prompts, prompt history, prompt sharing, and
          evaluations; it is now retired.
        </td>
      </tr>
      <tr>
        <td><strong>Messages API</strong></td>
        <td>
          Anthropic’s direct API for sending a sequence of messages to Claude.
          The developer manages conversation history and tool-execution loops.
        </td>
      </tr>
      <tr>
        <td><strong>Message</strong></td>
        <td>
          A request or response turn in the Messages API. User messages carry
          input; assistant messages represent Claude’s output.
        </td>
      </tr>
      <tr>
        <td><strong>Content block</strong></td>
        <td>
          A typed component within a message, such as text, an image, a
          tool-use block, or a tool-result block.
        </td>
      </tr>
      <tr>
        <td><strong>System prompt</strong></td>
        <td>
          Persistent instructions or context supplied separately from the
          user’s message.
        </td>
      </tr>
      <tr>
        <td><strong>Tool use</strong></td>
        <td>
          Anthropic’s term for Claude requesting that an application invoke a
          defined tool.
        </td>
      </tr>
      <tr>
        <td><strong>Tool definition</strong></td>
        <td>
          The name, description, and input schema that explain to Claude how a
          tool can be used.
        </td>
      </tr>
      <tr>
        <td><strong>Tool-use block</strong></td>
        <td>
          Claude’s structured request to call a tool, including the tool name
          and input arguments.
        </td>
      </tr>
      <tr>
        <td><strong>Tool-result block</strong></td>
        <td>
          The application’s returned result after executing Claude’s requested
          tool.
        </td>
      </tr>
      <tr>
        <td><strong>Extended thinking</strong></td>
        <td>
          A mode that allocates additional model computation for difficult
          reasoning tasks. The API may expose a summary or related thinking
          content rather than treating internal reasoning as ordinary answer
          text.
        </td>
      </tr>
      <tr>
        <td><strong>Vision</strong></td>
        <td>
          Claude’s ability to interpret images included in a message.
        </td>
      </tr>
      <tr>
        <td><strong>Structured outputs</strong></td>
        <td>
          A method for asking Claude to return data in a defined machine-readable
          shape, such as JSON matching a schema.
        </td>
      </tr>
      <tr>
        <td><strong>Prompt caching</strong></td>
        <td>
          Reuse of a stable prompt prefix across requests. Anthropic supports
          automatic caching or explicit cache breakpoints.
        </td>
      </tr>
      <tr>
        <td><strong>Streaming</strong></td>
        <td>
          Receiving response events incrementally as Claude generates them
          rather than waiting for the complete response.
        </td>
      </tr>
      <tr>
        <td><strong>Batch testing / Message Batches</strong></td>
        <td>
          Running many requests together for evaluation, experimentation, or
          large-scale processing, typically with different latency and pricing
          characteristics from interactive calls.
        </td>
      </tr>
      <tr>
        <td><strong>Workspace</strong></td>
        <td>
          An organizational boundary for API keys, access control, usage, and
          related Console resources.
        </td>
      </tr>
      <tr>
        <td><strong>Managed Agents</strong></td>
        <td>
          Anthropic-managed infrastructure for deploying stateful autonomous
          agents with persistent event history.
        </td>
      </tr>
      <tr>
        <td><strong>MCP</strong></td>
        <td>
          Model Context Protocol, an open protocol for standardizing how
          applications provide context and tools to language models.
        </td>
      </tr>
      <tr>
        <td><strong>HHH</strong></td>
        <td>
          “Helpful, honest, harmless,” an Anthropic research framework
          describing desirable model behavior.
        </td>
      </tr>
    </tbody>
  </table>

  <h2>Prompt-building vocabulary</h2>

  <table>
    <thead>
      <tr>
        <th scope="col">Term</th>
        <th scope="col">Meaning</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td><strong>Role</strong></td>
        <td>
          The function the model is asked to perform, such as editor, analyst,
          tutor, or support agent.
        </td>
      </tr>
      <tr>
        <td><strong>Objective</strong></td>
        <td>The concrete outcome the model should produce.</td>
      </tr>
      <tr>
        <td><strong>Constraint</strong></td>
        <td>
          A rule limiting content, format, tone, sources, length, or permitted
          actions.
        </td>
      </tr>
      <tr>
        <td><strong>Context</strong></td>
        <td>
          Background information the model needs to complete the task.
        </td>
      </tr>
      <tr>
        <td><strong>Delimiter</strong></td>
        <td>
          A marker—such as XML tags, headings, or triple backticks—that
          separates instructions from data.
        </td>
      </tr>
      <tr>
        <td><strong>Few-shot example</strong></td>
        <td>
          An example input-output pair included to demonstrate the desired
          behavior.
        </td>
      </tr>
      <tr>
        <td><strong>Zero-shot prompt</strong></td>
        <td>
          A prompt that gives instructions without examples.
        </td>
      </tr>
      <tr>
        <td><strong>One-shot prompt</strong></td>
        <td>A prompt containing one example.</td>
      </tr>
      <tr>
        <td><strong>Few-shot prompting</strong></td>
        <td>
          Prompting with several examples to establish a pattern.
        </td>
      </tr>
      <tr>
        <td><strong>Output format</strong></td>
        <td>
          The required shape of the response, such as Markdown, JSON, a table,
          or a fixed set of fields.
        </td>
      </tr>
      <tr>
        <td><strong>Schema</strong></td>
        <td>
          A formal description of permitted data fields, types, and structure,
          usually expressed as JSON Schema.
        </td>
      </tr>
      <tr>
        <td><strong>Grounding</strong></td>
        <td>
          Supplying authoritative context—documents, database results, or
          retrieved sources—so the model’s answer is based on that material.
        </td>
      </tr>
      <tr>
        <td><strong>Retrieval-augmented generation (RAG)</strong></td>
        <td>
          Retrieving relevant external information and placing it into the
          model’s context before generation.
        </td>
      </tr>
      <tr>
        <td><strong>Hallucination</strong></td>
        <td>
          An answer that sounds plausible but is unsupported, incorrect, or
          invented.
        </td>
      </tr>
      <tr>
        <td><strong>Guardrail</strong></td>
        <td>
          A rule or mechanism that restricts unsafe, invalid, off-topic, or
          unauthorized behavior.
        </td>
      </tr>
      <tr>
        <td><strong>Refusal</strong></td>
        <td>
          A response declining to perform a request because of safety, policy,
          capability, or authorization limits.
        </td>
      </tr>
      <tr>
        <td><strong>Prompt injection</strong></td>
        <td>
          Untrusted content attempting to override the intended instructions,
          often through retrieved documents, web pages, or user-provided files.
        </td>
      </tr>
      <tr>
        <td><strong>Agent loop</strong></td>
        <td>
          The repeated cycle of model reasoning, tool invocation, receiving
          tool results, and continuing until the task is complete.
        </td>
      </tr>
      <tr>
        <td><strong>Stateless</strong></td>
        <td>
          The service does not automatically retain the prompt or conversation
          for the next request; the application must preserve and resend state.
        </td>
      </tr>
      <tr>
        <td><strong>Stateful</strong></td>
        <td>
          Conversation or task state is retained and managed across requests by
          the application or platform.
        </td>
      </tr>
      <tr>
        <td><strong>Productionization</strong></td>
        <td>
          Turning an experiment into a dependable application with
          authentication, monitoring, error handling, evaluation, cost
          controls, and safety measures.
        </td>
      </tr>
    </tbody>
  </table>

  <h2>API and evaluation language</h2>

  <table>
    <thead>

    </thead>

        </td>

      </tr>
      <tr>

        <td>
          Sending a failed request again, usually with exponential backoff for

        </td>
      </tr>
      <tr>
        <td><strong>Timeout</strong></td>
        <td>
          The maximum time an application waits before treating a request as
          failed.
        </td>
      </tr>
      <tr>
        <td><strong>Throughput</strong></td>
        <td>
          The volume of requests or tokens processed per unit of time.
        </td>
      </tr>
      <tr>
        <td><strong>Cost per request</strong></td>
        <td>
          The price associated with input tokens, output tokens, tool calls,
          cached tokens, or other billable operations.
        </td>
      </tr>
      <tr>
        <td><strong>Determinism</strong></td>
        <td>

        </td>
      </tr>
      <tr>
        <td><strong>Regression</strong></td>
        <td>

        </td>

        <td><strong>Golden set</strong></td>

        <td>

        <td>

  <h2>Phrases that sound fluent</h2>

  <ul>
    <li>
      “I’ll prototype this in the Playground, then export the raw request and
      move it to the Responses API.”
    </li>
    <li>
      “The system instructions define the behavior; the user message supplies
      the task-specific input.”
    </li>
    <li>
      “This is a tool-use workflow, not merely text generation—the model
      proposes a function call, and the application executes it.”
    </li>
    <li>
      “Let’s require Structured Outputs so downstream code receives
      schema-valid JSON instead of parsing free-form prose.”
    </li>
    <li>
      “The prompt has a large static prefix, so prompt caching should reduce
      repeated input cost and latency.”
    </li>
    <li>
      “The Anthropic Playground is a thin interface over the Messages API, so
      the request and response shape should match what we implement in code.”
    </li>
    <li>
      “We need an eval set before claiming the new prompt is better.”
    </li>
    <li>
      “The model is grounded in retrieved documents, but retrieval quality and
      prompt-injection resistance still need testing.”
    </li>
  </ul>

  <h2>The key distinction</h2>

  <p>
    <strong>Playground / Console is the experimentation surface; the API is the
    integration surface.</strong>
  </p>

  <p>
    You use the browser tool to select a model, refine instructions, inspect
    tokens and raw payloads, test tools or schemas, and export code. Your
    application then reproduces that request through OpenAI’s Responses API or
    Anthropic’s Messages API. In Anthropic’s case, the current Playground is
    directly built on Messages API requests.
  </p>
